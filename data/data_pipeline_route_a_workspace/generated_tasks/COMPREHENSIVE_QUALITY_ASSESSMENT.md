## 可靠性问题详细分析

### 问题1: Python代码质量不稳定

**案例**: fm_20260819_002  
**错误**: 
```python
File "/tmp/tmp436sv14p.py", line 127
    ws_t.cell(row=r, column=5
             ^
SyntaxError: '(' was never closed
```

**影响**: 
- Golden workbook生成失败
- 任务直接跳过，无输出
- 用户体验差（无错误恢复）

**根本原因**: 
LLM生成的Python代码未经验证直接执行

**修复建议**:
```python
# 在执行前添加语法检查
import ast
try:
    ast.parse(generated_code)
except SyntaxError as e:
    logger.error(f"Generated code has syntax error: {e}")
    # Option 1: 重试（将错误反馈给LLM）
    # Option 2: 使用更保守的代码生成prompt
    # Option 3: 跳过并记录
```

**优先级**: 🔴 CRITICAL - 必须修复

---

### 问题2: API超时持续存在

**案例**: fm_20260819_003  
**超时模式**:
- 15:34:40 - 请求开始
- 15:44:40 - 第1次重试（10分钟后）
- 15:54:40 - 第2次重试（20分钟后）
- 16:04:41 - 请求失败（30分钟后）

**影响**:
- 阻塞整个批次生成
- 浪费计算资源
- 用户等待时间过长

**根本原因分析**:

**假设1: API服务器负载**
- 证据: 健康检查返回200
- 可能性: 中等
- 验证方法: 检查API服务器日志

**假设2: L4任务复杂度过高**
- 证据: 0/2 L4任务在batch 3成功（vs batch 1的高成功率）
- 可能性: 高
- 验证方法: 对比L3和L4的prompt复杂度

**假设3: 大型seed + L4组合**
- 证据: seed_collection_0039 (450KB, 58K cells, 0 formulas)
- 可能性: 高
- 验证方法: 测试小型seed + L4

**修复建议**:
1. **立即**: 设置max timeout (15分钟)，超时后优雅失败
2. **短期**: 为L4任务过滤大型seeds (> 400KB)
3. **长期**: 实现分步生成（先生成简单公式，再增加复杂度）

**优先级**: 🔴 CRITICAL - 严重影响用户体验

---

### 问题3: L4难度任务不可靠

**数据**:

| 批次 | L3成功率 | L4成功率 |
|------|----------|----------|
| test_batch_fm | - | 高（具体数据未统计） |
| batch_fm_fixed_v2 | 1/1 (100%) | 0/2 (0%) |

**观察**:
- Batch 3中所有L4任务都失败了
- 失败模式不同（代码错误 + 超时），但都发生在L4
- L3任务成功

**假设**:
L4的scenario generation prompt可能生成过于复杂的任务描述，导致：
1. Golden workbook生成时LLM试图创建过于复杂的公式
2. 生成的代码更长更复杂，容易出现语法错误
3. API响应时间过长

**验证方法**:
1. 比较L3和L4的scenario generation prompt
2. 统计L3 vs L4生成的代码长度和复杂度
3. 分析L4任务的答案区域数量和公式复杂度要求

**修复建议**:
1. **审查L4 prompt**: 降低复杂度要求
2. **限制L4答案区域**: 不超过4个区域
3. **渐进式生成**: L4任务分多步生成，每步验证

**优先级**: 🟠 HIGH - 影响L4任务的可用性
