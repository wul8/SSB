# 电子表格领域「意图驱动」Query 生成管线

把 Agent-as-Annotators 的核心逻辑（环境 → 画像 → 任务 → 轨迹）迁移到电子表格领域。与 A3 通用方法的两处差异：一是对「环境状态」（具体 Excel 表格结构）做显式建模，二是用 Few-shot 种子轨迹指导 Query 生成。

## 总览

| 步骤 | 输入 | 输出 |
| --- | --- | --- |
| Step 1 环境分簇 | SpreadsheetBench 2 / MiMoTable / T2R-Bench / Sheetpedia | `{领域, 复杂度, 常见操作}` 的环境簇列表 |
| Step 2 画像生成 | 每个环境簇 | 每簇 10–20 个人物画像（背景 + 专业知识 + 工具熟练度） |
| Step 3 任务种类定义 | 环境簇 + 画像 | 「环境 × 任务种类」矩阵（区分通用 / 特定） |
| Step 4 Query + 轨迹生成 | Few-shot 种子（环境状态 + Query + 轨迹 + 答案） | 新 Query + 预期操作序列 + 标准答案工作簿 |

---

## Step 1：构建环境分类体系

类比 Web 环境（电商、论坛、GitLab），把电子表格按领域和结构分簇。

| 维度 | 说明 | 示例 |
| --- | --- | --- |
| 领域标签 | 从数据集中提取或人工打标 | 金融、人力资源、销售、物流、教育、制造 |
| 结构复杂度 | 单表 / 多表 / 超大宽表 | 金融报表多为多表跨 sheet；物流常见单表大宽表 |
| 操作类型 | 该领域常见操作 | 金融：建模、调试；销售：汇总、可视化 |

数据来源：

- 已有标签：SpreadsheetBench 2（含领域标签）、MiMoTable（7 个领域）、T2R-Bench（19 个工业领域）
- 无标签但规模大：Sheetpedia、EUSES —— 用 LLM 做领域分类（参考 MiMoTable 的分类方式）

**产出**：环境簇 = `{领域, 复杂度, 常见操作类型}`，每个簇对应一个「电子表格环境」。

---

## Step 2：生成人物画像簇

Web 领域的「买家 vs 管理员」，对应到电子表格领域是「财务分析师 vs CFO vs 审计师」。对每个环境簇用 LLM 生成 10–20 个多样化画像。

```json
{
  "environment": "金融财务",
  "personas": [
    {"background": "投行分析师", "expertise": "DCF建模、LBO、财务预测"},
    {"background": "财务总监", "expertise": "合并报表、预算控制、KPI监控"},
    {"background": "审计师", "expertise": "数据验证、异常检测、合规检查"}
  ]
}
```

可再叠加一层「工具熟练度画像」，用于控制任务难度：

- 初级：SUM、AVERAGE
- 中级：VLOOKUP、IF、PivotTable
- 高级：INDEX/MATCH、数组公式、Power Query

**产出**：每个环境簇对应一组画像（背景 + 专业知识 + 工具熟练度）。

---

## Step 3：定义任务种类（Goals）

明确每个环境簇下有哪些任务种类，并区分环境特定与跨环境通用。

| 任务种类 | 金融财务 | 人力资源 | 销售管理 | 跨环境通用 |
| --- | --- | --- | --- | --- |
| Template 填充模板 | 预算模板 | 员工信息模板 | 销售模板 | 是 |
| Debugging 调试 | 公式错误 | VLOOKUP 失效 | 数据不一致 | 是 |
| Financial Modeling | 独家 | — | — | 否 |
| 数据汇总 | 按季度 | 按部门 | 按产品 | 是 |
| 可视化 | 趋势图 | 结构图 | 柱状图 | 是 |
| 跨表合并 | 多报表 | 多部门 | 多渠道 | 是 |

**产出**：「环境 × 任务种类」矩阵，明确每个环境的任务覆盖广度。

---

## Step 4：Query 生成

先用 Few-shot 种子数据让 LLM 学会结合环境状态生成 Query，再批量泛化。

### 4.1 Few-shot 种子的构造

每个示例包含环境状态、画像、任务种类、Query、轨迹、答案：

```json
{
  "environment": {
    "domain": "金融财务",
    "sheets": [
      {"name": "利润表", "columns": ["年份", "营收", "成本", "毛利"], "rows": 10},
      {"name": "资产负债表", "columns": ["年份", "资产", "负债", "权益"], "rows": 10}
    ],
    "cross_sheet_relations": "利润表的'营收'与资产负债表的'资产'无直接依赖；毛利 = 营收 - 成本"
  },
  "persona": {
    "background": "投行分析师",
    "expertise": "财务建模、DCF",
    "goal": "为某公司构建未来5年的财务预测模型"
  },
  "task_type": "Template / Debugging / Generation",
  "query": "作为投行分析师，我需要为该公司构建未来5年的财务预测模型。请基于利润表和资产负债表的历史数据，在'预测'工作表中完成：1) 预测营收以每年5%增长；2) 毛利率保持在35%；3) 预测资产随营收等比例增长。",
  "trajectory": [
    {"step": 1, "action": "创建新工作表'预测'", "cell": null},
    {"step": 2, "action": "复制利润表的年份列到预测表", "range": "利润表!A2:A11 → 预测表!A2:A11"},
    {"step": 3, "action": "写入公式到预测表的营收列", "formula": "=B2*1.05"}
  ],
  "answer": "预测表已完整生成，包含5年预测数据，所有公式正确。"
}
```

### 4.2 批量生成新 Query

对每个目标工作簿（Sheetpedia 或 MiMoTable），LLM 依次：

1. **读取环境状态**：有哪些 sheet、列名是什么、有哪些跨表关系
2. **匹配画像和任务种类**：从 Step 2、Step 3 中各选一个
3. **参考 Few-shot 种子**：学习 Query 结构、术语风格、任务复杂度
4. **生成新 Query + 预期轨迹**：输出完整 Query，并规划实现步骤

**关键约束**：生成的 Query 必须能在当前这个具体工作簿中完成，不能提出超出其数据范围或结构的要求。

### 4.3 标准答案的生成

与 Web 领域最大的不同：网页任务的标准答案是轨迹（点击序列），电子表格的标准答案是**最终工作簿状态 + 操作序列**。

分工如下：

- **LLM** 只负责生成 Query（语义理解和场景构建）
- **确定性引擎**（pandas / openpyxl）负责执行，生成 100% 正确的标准答案工作簿
- **验证** 用 Spreadsheet-RL 的评估 API 或自建脚本检查最终工作簿是否符合预期

原因：LLM 难以精准生成 `=VLOOKUP(...)` 这类公式的坐标，代码引擎可以做到 100% 正确。

---

## 核心设计点

1. **环境分类体系**：按领域和结构对电子表格分簇，替代 Web 领域的「电商/论坛/GitLab」分类
2. **画像驱动多样性**：用「背景 × 专业知识」组合生成大量用户画像，保证 Query 多样性
3. **Few-shot 指导 Query 生成**：种子数据（含环境状态 + 轨迹）教 LLM 读懂具体工作簿结构，生成可执行 Query
4. **标准答案确定性生成**：LLM 只出 Query，代码引擎算答案，避开 LLM 写公式出错

生成数据来自 Sheetpedia / MiMoTable，与 SpreadsheetBench 2 的数据来源不重叠，因此不影响打榜 SpreadsheetBench 2 的目标。
